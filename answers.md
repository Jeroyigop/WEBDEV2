# Lab 8 — Database-Backed CRUD Application

## Implementation evidence

### Task 1 — Repository

`PetRepository` extends `JpaRepository<Pet, Long>` and supplies the derived and custom query methods:

```java
public interface PetRepository extends JpaRepository<Pet, Long> {
    List<Pet> findBySpeciesIgnoreCase(String species);
    List<Pet> findByNameContainingIgnoreCase(String keyword);

    @Query("SELECT DISTINCT p.species FROM Pet p")
    List<String> findAllSpecies();
}
```

`Pet` has a generated primary key and a non-null, unique microchip column:

```java
@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;

@Column(name = "microchip_number", unique = true, nullable = false)
@NotBlank
private String microchipNumber;
```

The integration test's seed row is `CHIP-0001 / Luna / Cat / Siamese`. The test also confirms `GET /api/pets` returns it:

```text
GET /api/pets -> 200 OK
[{"id":1,"microchipNumber":"CHIP-0001","name":"Luna","species":"Cat","breed":"Siamese"}]
```

### Task 4 — Transaction rollback

The batch implementation flushes after each save so a constraint violation is raised inside the transaction:

```java
@Transactional
public void batchRegister(List<Pet> pets) {
    for (Pet pet : pets) {
        validate(pet);
        petRepository.save(pet);
        entityManager.flush();
    }
}
```

The test submits the first pet with `CHIP-BATCH-NEW`, followed by a duplicate `CHIP-0001`. It receives `DataIntegrityViolationException`, then verifies both the repository count and lookup for the first pet remain unchanged. This proves the prior insert was rolled back.

The SQL log shows an insert being issued for the first row, but no commit of that row when the duplicate triggers the unique constraint on `microchip_number`.

### Task 5 — Persistence debugging

Three defects were identified in the broken snippet:

1. `@Id` has no `@GeneratedValue`, so JPA does not request an identity value from the database. The new entity therefore reaches persistence with no generated ID.
2. The `species` field is omitted, despite it being required by the Pet model and API.
3. `microchipNumber` is set to `null`, violating `nullable = false` and the uniqueness contract.

**Debugging process:**

1. **Stack trace:** Saving with a null required microchip fails validation or, without Bean Validation, reaches Hibernate as a `ConstraintViolationException`. Identity still has to be generated by a `@GeneratedValue` mapping.
2. **SQL log:** Hibernate issues no valid completed insert for the entity. With `spring.jpa.show-sql=true`, the output exposes the INSERT's null column and/or the uniqueness constraint failure. Hibernate parameter binding is enabled through `logging.level.org.hibernate.orm.jdbc.bind=TRACE`.
3. **Fix:** Add `@GeneratedValue(strategy = GenerationType.IDENTITY)` to `id`; restore and map `species`; require a nonblank `microchipNumber` in `Pet`, validate it in `PetService`, and let the database enforce `unique=true, nullable=false`.

The fixed endpoint and service now reject invalid requests before persistence and successfully process complete Pet entities.
